# 뉴스수집기 기능 개발 워크플로

새 기능을 개발할 때 브랜치 생성부터 메인 병합까지 순서대로 진행한다.

이 저장소는 Vercel 프로젝트 `ai-news`(팀 `tomas-664e`)에 연결되어 있다. 메인 브랜치에 push하면 곧바로 운영(Production)에 배포되고, 다른 브랜치에 push하면 프리뷰(Preview)로 배포된다. 그래서 작업 브랜치를 먼저 push해 프리뷰에서 확인하고, 확인이 끝난 뒤에만 메인에 병합해 push한다.
브랜치 이름: $ARGUMENTS

이 저장소의 메인 브랜치는 `main`이 아니라 `master`일 수 있다. 아래에서 "메인"은 `git symbolic-ref refs/remotes/origin/HEAD`로 확인한 기본 브랜치를 뜻한다 (확인이 안 되면 `main`, 없으면 `master`).

## 1. 현재 상태 확인

1. `git status --short --branch`로 현재 브랜치와 변경 사항을 보여준다.
2. 현재 브랜치가 메인이 아니면 "⚠️ 지금은 메인이 아닌 `<브랜치>` 브랜치에 있습니다."라고 경고하고, 메인으로 이동할지 AskUserQuestion으로 물어본다.
   - 이동하기로 하면 `git switch <메인>`으로 이동한다.
   - 이동하지 않기로 하면 여기서 멈춘다.
3. 커밋하지 않은 변경 사항이 있으면 브랜치를 옮기기 전에 알려주고, 어떻게 할지(먼저 커밋 / stash / 중단) 물어본다. 사용자 확인 없이 변경 사항을 버리지 않는다.

## 2. 새 브랜치 만들기

- `$ARGUMENTS`가 있으면 그 이름으로 `git switch -c $ARGUMENTS`를 실행한다.
- `$ARGUMENTS`가 비어 있으면 "어떤 기능을 개발할 건가요?"라고 묻는다. 답을 받으면 영어 소문자와 하이픈 형식의 브랜치 이름을 2~3개 제안하고(예: `feature/category-filter`, `add-category-filter`) AskUserQuestion으로 고르게 한다.
- 같은 이름의 브랜치가 이미 있으면 알려주고 다른 이름을 제안한다.

## 3. 개발 시작 안내

브랜치를 만든 뒤 다음을 안내한다.

1. "✅ `<브랜치>` 브랜치가 만들어졌습니다. 이제 개발을 시작하세요!"
2. `CLAUDE.md`, `AGENTS.md`를 읽고 이 프로젝트의 기술 스택과 컨벤션을 짧게 정리해 보여준다. 최소한 다음을 포함한다.
   - 기술 스택: Next.js 버전과 주의점, 인증, DB/ORM, AI 호출 방식, Notion 연동, 스타일링
   - 컨벤션: 구현 전 `PRD.md`, UI 작업 전 `ui.md` 확인, 색상은 토큰 사용, Next.js API는 `node_modules/next/dist/docs/` 먼저 확인, 캐싱은 Cache Components 방식 등
   - 검사 명령: `npm run lint`, `npm run build`
3. "개발이 끝나면 '완료' 또는 'done'이라고 입력하세요."라고 알려준다.

이후 사용자가 요청하는 개발 작업은 평소처럼 돕는다.

## 4. 완료 처리 (사용자가 '완료' 또는 'done'을 입력했을 때)

1. 지금 작업 브랜치에 있는지 확인한다. 메인에 있으면 멈추고 알린다 (메인에서 push하면 바로 운영 배포된다).
2. `git status --short`와 `git diff --stat`으로 변경된 파일 목록을 보여준다. 변경 사항이 없으면 알려주고 멈춘다.
3. `npm run lint`와 `npm run build`를 실행해 결과를 보여준다. 실패하면 오류를 보여주고 고칠지 물어본다. 실패한 채로 push하지 않는다.
4. 변경 내용을 보고 커밋 메시지를 제안한다. 형식은 기존 커밋(`git log --oneline -5`)을 따른다: `한국어 요약: 무엇을 바꿨는지 한 줄 설명`.
5. AskUserQuestion으로 확인을 받는다 (제안대로 커밋하고 프리뷰 배포 / 메시지 수정 / 취소).
6. 확인을 받으면 변경 파일을 작업 브랜치에 커밋한다. `.env*` 같은 비밀 파일은 커밋하지 않는다.

## 5. 프리뷰 배포 확인

1. 작업 브랜치를 push한다: `git push -u origin <브랜치>`. 메인은 push하지 않는다.
2. Vercel MCP의 `list_deployments`(`app: "ai-news"`, `branch: <브랜치>`)로 이번 커밋의 배포를 찾는다. `target`이 `production`이 아니라 프리뷰인지 확인하고, `state`가 `READY` 또는 `ERROR`가 될 때까지 기다린다. 기다릴 때는 짧은 sleep을 반복하지 말고 끝나는 조건으로 기다린다.
   - `ERROR`면 `list_deployment_events`로 빌드 로그를 보여주고, 고칠지 물어본다. 고칠 때는 작업 브랜치에서 고쳐 커밋하고 다시 push한다. 실패한 채로 병합하지 않는다.
3. `READY`면 프리뷰 주소를 알려준다.
   - 브랜치 주소: `https://ai-news-git-<브랜치>-tomas-664e.vercel.app` (브랜치에 새로 push할 때마다 최신 배포를 가리킨다)
   - 배포별 주소: `list_deployments` 결과의 `url`
4. 프리뷰를 볼 때 주의할 점을 함께 알린다.
   - 프리뷰 주소는 Vercel 배포 보호가 켜져 있어 Vercel에 로그인한 사람만 열 수 있다.
   - 프리뷰도 운영과 같은 DB·Notion을 쓴다. 프리뷰에서 '뉴스 가져오기'나 'Notion 저장'을 누르면 실제 데이터가 바뀐다.
5. AskUserQuestion으로 다음 단계를 묻는다 (프리뷰 확인 끝, 메인에 병합하고 운영 배포 / 더 고치기 / 여기서 멈추기).
   - '더 고치기'면 개발을 계속 돕고, 다시 '완료'를 입력하면 4장부터 반복한다.
   - '여기서 멈추기'면 브랜치와 프리뷰를 그대로 두고 7장 요약으로 넘어간다.

## 6. 메인 병합과 운영 배포 (사용자가 병합을 고른 뒤에만)

1. `git switch <메인>` 후 `git pull --ff-only origin <메인>`으로 최신 상태를 받는다.
2. `git merge --no-ff <브랜치>`로 병합한다. 충돌이 나면 충돌 파일을 보여주고 멈춘 뒤 어떻게 할지 물어본다.
3. `git push origin <메인>`으로 push한다. 이 push가 운영 배포를 시작한다.
4. `list_deployments`(`app: "ai-news"`, `target: "production"`)로 이번 병합 커밋의 운영 배포가 `READY`가 될 때까지 확인한다. `ERROR`면 빌드 로그를 보여주고, 이전 운영 배포는 그대로 유지된다는 점과 함께 어떻게 할지 물어본다.
5. 운영 사이트 https://ai-news-theta-ruby.vercel.app 에 이번 변경이 반영됐는지 가능한 범위에서 확인한다 (예: 응답 HTML에 새 문구가 있는지).

## 7. 작업 요약

끝나면 다음을 정리해 보여준다.

- 브랜치 이름과 병합 대상 브랜치 (병합하지 않았으면 그렇다고 쓴다)
- 커밋 메시지와 커밋 해시 (병합 커밋 포함)
- 변경 파일 목록 (추가/수정/삭제)
- 구현한 기능 요약 (2~4줄)
- 프리뷰 주소와 배포 상태, 운영 배포 상태
- 다음에 할 일 제안 (예: 작업 브랜치 삭제 `git branch -d <브랜치>`와 원격 브랜치 삭제 `git push origin --delete <브랜치>`)
